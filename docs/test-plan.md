## 5. 顺序问题（写在这里，免得再犯）

正确顺序：

1. 功能写完
2. 分层自测（引擎层 / 接口层 / 组件层）
3. **把界面摆到你面前，你点，你提意见**
4. 按意见改，改完做回归
5. 全绿之后才打包
6. 装一遍确认安装器本身没问题

这轮我把 5、6 插到了 3 前面，代价是：

- 改一次代码就要重新打一次包、重装一次（每次 12 秒编译 + 40MB 拷贝）
- "能装上了"这件事本身会制造"已经做完了"的错觉
- 真正该花时间的 B4/B5/B6/B7/B8 全是空的，反而先把 D 段做绿了

所以接下来：**换图 → 跑完 A/B/C → 你验收 → 再打包，一次打完。**

## 6. 执行方式

```
python tools/accept.py          # 全跑，约 2 分钟
python tools/accept.py B6       # 只跑某段（A / B1 / B2 / B4 / B5 / B6 / B7 / B10 / C）
python tools/accept.py --keep   # 保留 .cache/accept 下的测试文件
```

- 逐条打印 `PASS` / `FAIL` / `SKIP`，每条都带**实测值**（字节数、状态、端口、用了几秒）

- 需要真点鼠标的项不硬凑，单独列在 `docs/manual-checklist.md`

顺带在这次验收里发现并修掉的 3 个真问题：

1. **快捷目录按钮点亮的可能不是自己** —— "上次保存"和"程序目录"经常是同一个文件夹，
   原来按文字匹配会把前一个点亮。改成把被点的按钮一起传下去。
2. `intents.open_path()` 打开目录时没走 `reveal()`，而是直接 `Popen(explorer)`，
   两套代码做同一件事，改一处漏一处。
3. 测试服务最初不支持 HTTP Range，导致"暂停再继续"看起来像续传坏了 ——
   这是**测试工具的缺陷**，不是程序的，但差点被当成 bug 修错地方。

做备注这一轮又修掉一个测试自身的坑：**测试引擎和真程序共用 `conf/session`**，
前几轮测试下到 `.cache/accept/dl` 的死任务全留在 session 里，下次启动时挤占并发位，
新任务排队迟迟不 active —— B6.1 因此假失败。现在测试引擎用独立的
`conf/aria2.test.conf` / `session.test` / `aria2.test.log`，真程序的 session 也顺手清干净了。

还剩两件只能人来做：真机听声音/看系统通知，以及关掉程序重开能不能续传（跨进程）。

不是数"桌上摆了几碗"：用户说的是"今天下载超过 3 个以后躺沙发"，不是"同时下 3 个"。

弃用两张，代码和素材都删了：`full`（仰头谄媚，用户第一次说不要）、
`eat`（馋嘴，用户第二次点名"一脸谄媚"）。`build_pet.py` 的 junk 清单一并更新，
`selfcheck.py` 只查还在用的那三张。

### 8.1 两个坑，都跟"什么算下完"有关

**坑一：BT 下完会继续做种，aria2 仍报 `active`（`seeder=true`）。**
原来 `downloading = 任何 active`，于是任务其实早就下完了，桌宠还以为在吃，
一直摆着"没吃饱"的脸 —— 用户截图里"下完半分钟了还是这张图"就是这么来的。
同一个原因还让**完成通知晚了整整一小时**（等做种结束 `status` 才变 `complete`）。
现在统一用 `TaskRow.is_finished`：`complete`，或者 `active && is_seeder`。

**坑二：姿势只在数据刷新时重算。**
"下完 12 秒"这种到点该换的，得有人叫它换。现在 `_tick()` 每 50ms 调一次
`_pick_mood()`，时间到就自己切，不用等下一次轮询。

气泡（单击桌宠弹出的那个白框）这轮保持：9 秒没人管自己收、鼠标移开 3 秒收、
全屏和贴边时跟着一起收。

## 9. 修掉的具体 bug（带根因，别再犯）

### 9.1 列表和表格之间一条白色空带（v0.9.5）

**现象**：左侧筛选列表和右侧任务表格之间，有一条从工具栏一直延伸到详情页的白色竖条，
窗口空着的时候特别显眼，用户以为是"漏了个面板"。

**根因**：`_build_ui` 把 `tree` 和右侧区域塞进了一个水平 `QSplitter`。
`tree.setFixedWidth(150)` 把它卡死在 150，但 `QSplitter` 首次分栏是按 `sizeHint` 算的——
`tree` 的 sizeHint 是 **256**。于是分栏宽度 256、控件只有 150，多出来的 106px 就是那条白带
（QSplitter 对"最大尺寸小于分栏"的子控件是原地留空，不会把分栏收回去）。

实测数据（探针打出来的）：

```
splitter sizes [256, 1103]   handleWidth 1
tree geometry  (0, 0, 150, 721)
tree sizeHint  QSize(256, 192)   min (150, 0)   max (150, 16777215)
```

**修法**：这个侧栏本来就是固定宽度、不给用户拖的，`QSplitter` 纯属多余。
换成 `QWidget + QHBoxLayout`（margins 0、spacing 0），树固定 150，右侧 `addWidget(right, 1)`。
修完 `table` 宽度从 1103 变成 1210，白带消失。

**教训**：固定宽度的控件别塞 QSplitter。要么让它可拖（别 setFixedWidth），
要么别用 QSplitter —— 两者混用就会出现"分栏比控件宽"的空洞。

## 10. 桌宠换图（v0.10.0）

用户要的不是"我帮他换图"，而是**设置里自己能换**：六张图各管一段状态，
他找自己的图丢进去就行，不用懂 PNG 尺寸也不用懂代码。

### 10.1 两层目录，不打架

| 位置 | 性质 | 谁写 |
|---|---|---|
| `assets/pet/<状态>.png` | 只读，装在 `_internal` 里，升级会被覆盖 | 构建脚本 `tools/build_pet.py` |
| `data/pet/<状态>.png` | 可写，绿色版整个文件夹能带走 | 用户在设置里换 |

查图只有一个入口 `pet_skin.sprite_path(name)`：**先看 `data/pet`，没有就回退内置**。
所以"换一张"就是往 `data/pet` 放一个同名文件，"还原"就是删掉它——不需要状态字段，
也不需要改任何配置，删了文件就自己回去了。

六个状态键是契约（v0.10.3 起就是这六个，eat 已删），改名字会让用户换好的图失效：

```
ciallo  idle_bowl  half  tease  idle_lying  sassy
```

顺序有意义：**就是一顿饭的顺序**，设置页也照这个排。

### 10.2 用户给的图必须能烂着进来

用户不会给你 512×512 透明 PNG，他给的多半是**白底 JPEG 截图**或者 1024 的杂图。
所以 `pet_skin.normalize()` 统一规整：

1. 超过 1024 先等比缩（纯 Python 逐像素处理，不缩跑不动）
2. **只在需要时抠白底**：图没有 alpha 通道，或者四个角都是不透明的白
3. 抠白底用**从四条边出发的洪水填充**，只抠跟边缘连通的近白像素
4. 按 alpha 求 bbox，裁掉空白边
5. 等比缩进 512×512 透明画布，居中，留 2% 边距

第 3 步是这套东西的关键：**如果用"所有白色都变透明"，图里白色的衣服、眼球、
高光会被吃成洞**。改成只抠连通边缘的白之后，主体内部的白完整保留——
验收里专门有一条断言，构造"白底 + 蓝椭圆 + 椭圆中间一个白点"，
抠完白点必须还在（`B11.7`）。

### 10.3 两个拒绝，都要说话

| 情况 | 行为 |
|---|---|
| 文件不是图（txt 改名 png） | 返回"这个格式读不进来，换成 PNG / JPG / WebP 试试"，不抛异常 |
| 整张全白 | 返回"这张图几乎全是白的，抠完什么都不剩"，**不写文件** |

第二条是刻意加的：全白图抠完是空的，如果照常写盘，用户会得到一张什么都不显示的
"白板桌宠"，还以为是自己没设置对。宁可明说。

失败一律不落盘，所以"换了半天没换成"不会把原来的图弄坏。

### 10.4 取消要能退回去

换图是**即时写盘 + 即时生效**的（换完马上能看到桌宠变样，不用重启）。
代价是"取消"按钮语义变脏，所以在打开选项对话框时把六张用户图快照进内存
（`_pet_orig`），`reject()` 时逐张比对、写回或删除，顺便让桌宠重画。
六张 512 PNG 约 1.8MB，代价可以忽略。

## 11. 选项里的数值（v0.10.1）

用户的原话是「很多用户不知道怎么设置，你应该有推荐值，能达到的上限和下限」。
做这件事的时候翻出**两个真 bug**，都是"界面显示的"和"引擎实际做的"对不上。

### 11.1 bug 一：单服务器最大连接填到 17–32，引擎根本起不来

界面原来允许 1–32，但 aria2 硬限制是 **1–16**，越界不是忽略而是**直接退出**：

```
$ aria2c --max-connection-per-server=17 --dry-run http://127.0.0.1:1/x
Exception: [AbstractOptionHandler.cc:69] errorCode=28
  -> max-connection-per-server must be between 1 and 16.
```

也就是说用户把这项"调大一点让它快些"，填了 20，程序下次启动时 aria2 起不来，
界面上只会看到"引擎没就绪"。这条现在有三道闸：

1. 界面范围 1–16（点不出 17）
2. `engine._clamp()` 在写配置前再夹一次（老 settings.json 里的越界值）
3. 验收里直接跑真 aria2 验证 17 会被拒（`B12.8`）

### 11.2 bug 二：做种时间的 0 被标成"不限"，实际是"下完立刻停"

`--seed-time=0` 在 aria2 里的含义是**下完立刻停止做种**，不是不限。
而界面把 0 的 specialValueText 写成了「不限」，默认值又正好是 0 ——
等于这个程序**从来没做过种**，用户却以为在无限做种。

改法：

| | 以前 | 现在 |
|---|---|---|
| 默认值 | 0（显示"不限"，实际不做种） | **60 分钟** |
| 0 的显示 | 不限 | **不做种**（说实话了） |
| 范围 | 0–100000 | 0–10080（7 天） |

想长期做种就把分钟数填大、分享率留 0（`--seed-ratio=0` 才是真的不限比例）。
两个条件是「谁先到按谁停」，界面上也写了这句。

## 12. 重复添加 / session 越攒越脏（v0.10.2）

这一条是**在用户真实下载过程中撞出来的**，不是想出来的：他挂了一个任务观察，
列表里慢慢长出三行红色的「错误」，全指着同一个种子。

### 12.1 现象

```
error  0.0%  [METADATA]78ed824b25b4e4937cb013a0719b7542cd20e3de
error  0.0%  [METADATA]78ed824b25b4e4937cb013a0719b7542cd20e3de
error  0.0%  [ANi] 亂世千金倪亞… - 03 [1080P]….mp4
```

三条错误信息一模一样：`InfoHash 78ed… is already registered.`

### 12.2 根因（两层）

1. **aria2 对重复种子不报错**：`addUri` 照样返回一个新 gid，然后那个任务立刻
   变成 error。所以"再加一次"在界面上表现为**多一行红字**，而不是"已经加过了"。
2. **`save-session` 是只追加、不清旧的**：这几条错误条目被写进 `conf/session`，
   下次启动 aria2 逐条读 → 第一条正常、后面全报 duplicate → 又写回 session。
   于是**每次启动都重现一遍，手动删掉下次还会回来**。这个是真的会一直烂下去。

实测的 session 文件（同一行 magnet 存了 4 遍）：

```
magnet:?xt=urn:btih:78ed…
 gid=b6015a3531ba3754
magnet:?xt=urn:btih:78ed…
 gid=7fe6430fbde58e88
magnet:?xt=urn:btih:78ed…
 gid=484e8662599b2b89
magnet:?xt=urn:btih:78ed…
 gid=aed772dac58ffad5
```

### 12.3 三层修法

| 层 | 做法 |
|---|---|
| 添加时 | `rpc.add_checked()`：建完立刻 `tellStatus`，如果是 duplicate 报错就把那条结果 `removeDownloadResult` 掉，返回 `(None, "duplicate")` |
| 提示 | 三个入口（API `POST /tasks`、拖放/剪贴板 `import_external`、新建任务对话框）都改走它；全重复时返回 `409 duplicate`「这个任务已经在列表里了，不用重复添加」，界面上则显示「N 个之前就加过了，没重复添加」 |
| 启动时 | `engine._dedupe_session()` 在拉起 aria2 之前把 session 按「同一个种子只留一条」清一遍（磁力比 `btih`，其余比整行小写）；起来后再 `_drop_dup_errors()` 把历史遗留的红行扫掉 |

`_dedupe_session` 是幂等的（第二次跑返回 0），空文件也不出错。


## 13. 桌宠姿势重排（v0.10.3）

用户看着设置页的六行和桌宠截图，指出三处"逻辑上有问题"：

1. **馋嘴那张没删干净** —— 他之前说过"一脸谄媚"那张不要了，删的是 `full`，
   而他指的是 `eat`（馋嘴凑过来）。这次连素材带状态一起删掉，设置页不再有这一行。
2. **半张脸被标成了"备用"** —— 他的原话是"这个明明是在整个下载过程中一直是这个图的"。

### 13.1 两条真 bug

**bug 一：做种被当成还在下载。**
BT 下完之后 aria2 不把任务标成 `complete`，而是一直 `active` + `seeder=true`，
做种时间（默认现在写的 60 分钟）结束才转 complete。旧代码写的是：

```python
active = [r for r in rows if r.status_code == "active"]   # 做种也算进来了
self.downloading = bool(active)
```

所以任务其实早就下完了，桌宠以为还在吃，一直摆着"没吃饱"的脸。
**同一个原因还让完成通知晚一小时**（`_scan_completion` 也只看 complete），
等于做种期间用户既收不到通知、又被桌宠盯着喊饿。

修法：`TaskRow.is_finished` —— `complete`，或者 `active && is_seeder`。
桌宠、完成通知、完整性校验、完成时间记录、气泡统计全部改走它。

**bug 二：姿势只在数据刷新时重算。**
`_pick_mood()` 原来只在 `update_data()` 里调。"下完 12 秒"是**纯时间条件**，
没有新数据进来就没人重算；轮询虽然一直在跑，但那次 `update_data` 只有在
任务列表变化时才走到换图分支（这次是借着 bug 一才暴露的）。
现在 `_tick()`（50ms 一次）里每帧调一次 `_pick_mood()`，到点就换。

### 13.2 定的顺序（用户原话 → 代码）

| 阶段 | 画哪张 | 条件 |
|---|---|---|
| 待命 | `ciallo` | 没任务，且今天下完不到 3 个 |
| 等饭 | `idle_bowl` | 有 waiting / paused，或磁力还在取种子 |
| 下载中 | `half` | 有真在下的（`active` 且非 seeder 非 meta）—— **全程这一张** |
| 下完 12 秒 | `tease` | `_done_until` 未到 |
| 吃撑了 | `idle_lying` | 待命态 + 今天下完 ≥3（`pet_day.json`，过零点归零） |
| 吐槽 | `sassy` | 名字踩词，停 8 秒（每个任务只一次） |

「今天几碗」是**当天累计下完数**，不是"桌上同时摆几碗"——用户说的
"今天下载超过 3 个以后躺沙发"是累计语义。存 `data/pet_day.json`，
程序重启不清零，桌宠内部 3 秒缓存一次（也顺带跨过零点）。

## 14. 表格列宽拖动（v0.10.4）

用户截图 + 一句话说清了：「我拖动大小和进度中间那条框，后面的并没有往后移，
只会把前面的那些项目缩小，这不是正常的设置逻辑」。

### 14.1 根因：`Stretch` 抢走了宽度

```python
hh.setSectionResizeMode(QHeaderView.ResizeMode.Interactive)
hh.setSectionResizeMode(COL_INDEX["name"], QHeaderView.ResizeMode.Stretch)  # ← 这行
```

Qt 的规则：拖动某列边界时，**被拖的列变宽，Stretch 列负责吸收差额**，

* 实际：拖大「大小」→ 右边的列一动不动，左边的「名称」默默窄了 80px

而且「名称」在左边，视觉上就是"我拖右边，左边缩水"，非常别扭。

思路没错，但"补宽"这件事本身会在拖动过程中改动别的列，引出下一轮问题。

## 16. 列宽「拖一下又复原」（v0.10.6）

用户：*"我松开手效果保留了，但我再去拖动以后，它会自动复原到某一个状态，
并不是我上次松开手的那个状态。拖一下给我复原，拖一下给我复原。"*

### 16.1 根因：双击表头 = "自动适配宽度"

不是列宽算法的问题，是 Qt 自带的一个交互：

```cpp
// QHeaderView::mouseDoubleClickEvent
resizeSection(logicalIndex, sectionSizeHint(logicalIndex));
```

**双击分隔线会把这一列拍回"内容宽度"**。用户连续两次拖动之间要是间隔短于
双击阈值（400ms），第二次就被当成双击 —— 宽度立刻回到 `sizeHint`，
看起来就是"被复原了"。

实测（脚本里发的真鼠标事件）：

```
初始    size= 70
拖+60   size=130
双击后  size= 45   ← 被拍回"合适宽度"，连带「名称」也被重新补宽
```

### 16.2 一并砍掉的：自动补宽

v0.10.4 那版会在拖完后自动把空白补给「名称」。配合上面的双击，
就变成"拖一下、位置全变一次"的混乱来源。既然右端空白现在已经是好看的
渐变星屑（第 15 节），**没必要再补宽**：

* 拖哪列就是哪列，任何别的列都不动
* 空出来的地方 → 右端那条渐变
* 撑出可视区 → 横向滚动条

代码上直接删掉了 `_fit_columns()` / `_on_section_resized()` / `_name_auto` /
`NAME_MIN_W`，`resizeEvent` 里也不再补列宽 —— 少一套状态机，就少一类 bug。

### 16.3 双击怎么办

`MainWindow.eventFilter` 把表头（和表头的 viewport）上的
`MouseButtonDblClick` 直接吃掉，返回 True。列宽只认手动拖的。

### 18.1 状态灯（新加的最左一列）

| 灯 | 含义 | 判定 |
|---|---|---|
| 🔵 蓝点 | 下载中 | `active` 且不是 seeder |
| 🟢 绿点 | 下载完成（没在上传） | `complete` |
| 🟢 绿点 + 外圈 | 下载完成、正在上传 | `active` + `is_seeder` |
| 🔴 红点 | 错误 | `error` 非空 |
| 🟡 黄色三角感叹号 | 文件不存在 | 下完了，但 `dir/name` 已经不在了 |

用户删了文件，系统不会通知下载器 —— 任务永远停在"已完成"，看起来一切正常。
所以轮询时给**已完成的任务**补一次 `stat`：

```python
gone = not (Path(r.dir) / r.name).exists()
```

* 只查 `is_finished` 的行（正在下的当然在，查了浪费）
* 结果缓存 8 秒（`_missing` 字典），别每轮 1.2 秒都去碰磁盘

### 18.3 多列排序（Shift 叠加）

原来的排序是写死的：`状态分组 → 添加时间`，表头点了没反应。
现在：

* **单击表头** = 换主键；同一列再点 = 翻方向
* **Shift + 单击** = 追加第二/第三/第四键（最多 4 个，满了挤掉最老的）
* 数字列（大小/进度/速度/剩余时间/完成时间）第一次点默认"大的在前"，文字列 A→Z
* 状态灯、打开文件夹、打开方式这三列点了不参与排序（没意义）
* 表头的 tooltip 会写出当前排序，比如"当前排序：状态 ↑，大小 ↓"
* 第一次单击时弹一次提示：`按住 Shift 再点一列，可以叠加排序`

实现就是稳定排序从最后一个键往前排：

```python
for key, desc in reversed(self._sort_keys):
    out.sort(key=lambda r, k=key: self._sort_value(r, k), reverse=desc)
```

用户场景（先按状态、再按大小，找某一类里最大的）在 `B17.12` 里直接验。

但 QSS 的 `image` 只认固定像素：在 125% / 150% 缩放下要么糊要么缺角。

| 状态 | 画法 |
|---|---|
| 未勾 | 白底 + 1.4px 圆角描边（`#E4E7EC`，悬停转主色蓝） |

### 22.7 独立的「上传」栏：怎么算"正在上传"（v0.10.15）

用户要求单独一栏看"哪些文件正在上传"，好及时停掉。关键是**判定口径**。

候选口径有三种，只有第三种能用：

| 口径 | 为什么不行 / 行 |
|---|---|
| 上传速度 > 0 | 会抖。没人来拉的时候速度就是 0，列表会一秒钟有一秒钟没，看着像坏了 |
| 状态是 active | 下载中也是 active，会把「干饭中」整个搬过来 |
| **aria2 报 `seeder=true`** | 这才是"下载已完成、文件在盘上、引擎正在对外供源"，正是用户说的上传期 |

所以 `seed` 栏的判定是：

```python
r.status_code == "active" and r.is_seeder and not r.error
```

三个连带处理：

1. **边下边传不算这一栏**：BT 下载时也会上传，但那时它是「干饭中」，
   上传速度在速度那一列能看见（`↓ x  ↑ y`）。
2. **「吃饱了」不再包含做种**：`complete` 才算吃饱；做种的单独一栏。
   以前做种的任务两边都不在，只能在「全部饭碗」里翻。
3. **磁力取种子阶段不算**（`is_meta`），它连饭都不是。

停掉的办法：右键任意一条 → **「停止分饭」**（`forcePause`，文件保留）。
提示语写在左栏该项的 tooltip 里。

状态栏也跟着分开数：

```
干饭中 2 碗 · 已吃饱 2 碗  ·  分饭中 1 个 · 共 8 碗
```

验证：`B21.18` 做种的任务只落在 seed 栏（不在 down / done）；
`B21.19` 下完没在传的仍然只在 done 栏。

## 26. 种子库 / .torrent 不再装成"已下好的文件"（v0.10.19）

用户实测：
- `.torrent` 老被当成"已经下载好的一个文件"混在任务列表里，比特彗星里没有这种；
- 需要一个**单独存放历史种子**的地方；
- 这些种子统一归到「给鱼群分饭」分类下面。

### 26.1 根因（两个叠在一起）

1. **HTTP `.torrent` 链接走的是普通 URL**：aria2 先把 .torrent 本体下下来（几十 KB，
   瞬间 complete），`follow-torrent` 再另起真正的 BT 任务。临时那条在界面上
   就是"一个已经下好的文件"。
2. **清理临时任务的代码一直在空转**：`_drop_meta_task()` 取 `self.api.rpc`，
   而 `ApiServer` 只有 `self.ctx.rpc` —— `getattr(..., None)` 拿到 None 直接 return，
   所以磁力/种子的"取种子"占位任务从来没被真正删掉（以前磁力那条也一样）。

### 26.2 做法

- `_drop_meta_task(row)` 改走 `self.engine.rpc`，临时任务真的会被
  `removeDownloadResult` 清掉；HTTP `.torrent` 的临时文件在删之前先读出来存档。
- `app/torrent_keep.py` 升级成真正的**种子库**：
  - `data/torrents/<infohash>.torrent` + `data/torrents/index.json`
    （名称/大小/gid/目录/来源/类型/添加时间）
  - 用自带 bencode 解析从种子里读 name 和总大小；旧版 `<gid>.torrent`
    会在 `entries()` 时自动补索引（不丢老存档）
  - `load_b64()` 同时支持按 infohash 和按 gid 取（老的「再分一轮饭」接口不变）
  - 磁力没有种子文件 → 只登记索引（`kind=magnet`），重分饭时贴回磁力
- 新增 `app/ui/torrent_library.py`：历史种子对话框（名称/大小/时间/来源、
  再分一轮饭 / 打开种子文件夹 / 删除存档）。
- 左栏「给鱼群分饭」下面挂一条 **「种子库 (N)」**，点开就是上面这个对话框；
  数量随轮询刷新。任务菜单和右键菜单也加了「种子库…」。
- 所有建任务路径都会存档：本地 `.torrent`、种子文件对话框、磁力、HTTP `.torrent`。
- 「吃饱了」筛选/计数排除 `is_meta`，临时任务不再混进"已下好"。

## 32. 校验误报「没吃干净」/ 备注列宽（v0.10.25）

用户截图：一个 100% 下完的文件状态显示「没吃干净 ✗」；手工 `integrity.check_file()`
对同一个文件是 **ok=True**。另外备注列默认 180px 太宽，只要刚好放下灰色提示即可。

### 32.1 误报的原因

`_maybe_verify` 在 aria2 刚报 `complete`（尤其带 `check-integrity` 重新挂上的任务）
那一刻就起线程校验；文件可能还在收尾/句柄未刷新，第一次校验偶尔失败，
`_on_verify_done` 直接把 `verify_ok=False` 缓存下来，`_verified` 又保证不再重验
→ 状态一直停在「没吃干净 ✗」。

### 32.2 修法

- `_on_verify_done`：第一次失败**先不落库**，登记 `_verify_attempts[gid]=1`，
  `QTimer.singleShot(4000, _retry_verify)` 补验一次；
- `_retry_verify`：任务还在、仍是 finished 才重验；两次都失败才标红；
- 备注列宽 `COLS` 里 `memo: 180 → 112`（实测提示文字宽 91px + 内边距 13px），
  默认刚好放下「＋ 双击这里写备注」。

### 32.3 验证

- `accept.py B23.11`：第一次失败只登记重试、不写 verify_map；
- `accept.py B26.13`：备注列默认宽度在 90–130 之间；
- 全量 `accept.py`：**281 通过 / 0 失败**；
- 实测重挂已完成任务后 `GET /api/v1/tasks?verify=1` 返回 `verify.ok=True`，

## 34. 重新分饭不再"多下完一碗"（v0.10.27）

- aria2 对**暂停中的 BT 任务**会报 `status=paused`、`totalLength=0`、
  `completedLength=0`（文件其实在磁盘上，大小也对）；
- 旧逻辑只看 aria2 状态：paused → 「放下筷子」，size 0 → 0%；
- 本机 `tasks.json` 里的 `finished_at` 才是"曾经下完"的事实，旧逻辑没拿它兜底。

### 38.2 修法（三层）

1. **TaskRow 以 finished 为准**：`finished_at` 存在时，即使是 paused/waiting，
   状态也显示「已完成」、绿点、100%，并留在「开饭了」；「放下筷子」筛选
   明确排除已完成的（`status==paused and not is_finished`）。
2. **aria2 0 大小兜底**：`row_from_aria2` 先看 `files[].length` 求和，
   再退回 tasks.json 记过的 `size`；finished 时 `done` 补成 size。
3. **自愈**：暂停任务没有 finished_at 时，按 infohash 从种子库/下载目录找 `.torrent`，
   用种子声明的总大小和磁盘文件/目录比对；相等就补记 finished_at + size
   （`_recover_task_size`，每 gid 只试一次，成功立刻 `store.save()`）。
   不删 `.aria2` 控制文件，不影响之后继续校验/做种。

### 38.3 验证

- `accept.py B28` **9 项**：paused+finished → 已完成/100%/绿点/在开饭了不在放下筷子；
  中途暂停仍算暂停；aria2 totalLength=0 时用本机 size 补；
  `target_complete()` 单文件大小比对。
- 当前用户的两个暂停任务已自愈落盘：`size` 456197959 / 695358700，
  都补了 `finished_at`，界面回到「开饭了」100%。
- 全量 `accept.py`：**302 通过 / 0 失败**；`testpet` 98 项。
